00Theory & Fundamentals

Before diving into syntax, it's essential to understand the fundamental differences between Python, C++, and C#. These languages represent different design philosophies and solve problems in distinct ways.

Language Categories & Paradigms

What is a Programming Paradigm?

A programming paradigm is a fundamental style or approach to programming that defines how we structure and organize code. Languages can support multiple paradigms, but often favor certain approaches.

Aspect Python C++ C#
Primary Paradigm Multi-paradigm (OOP, Functional, Procedural) Multi-paradigm (OOP, Procedural, Generic) Object-Oriented (with Functional features)
Execution Model Interpreted (bytecode) Compiled (native machine code) Compiled (IL → JIT to native)
Type System Dynamic, Strong Static, Strong Static, Strong
Memory Management Automatic (GC) Manual (with smart pointers) Automatic (GC)
Level High-level Low-level / Mid-level High-level

Compiled vs Interpreted: How Code Runs

Why Does This Matter?

Understanding how your code executes helps you write better programs, debug issues, and make informed decisions about performance optimizations.

Python: Interpreted Language

Python Execution Pipeline 
# Python's execution flow:
#
# Source Code (.py)
#        ↓
# [Python Interpreter]
#        ↓
# Bytecode (.pyc) ← Intermediate representation
#        ↓
# [Python Virtual Machine (PVM)]
#        ↓
# Execution (line by line)
#
# Characteristics:
# ✓ No separate compilation step needed
# ✓ Platform independent (.pyc runs anywhere)
# ✓ Easy debugging - errors at runtime with line numbers
# ✗ Slower than compiled languages (10-100x)
# ✗ Type errors discovered only at runtime

C++: Compiled to Native Code

C++ Compilation Pipeline 
// C++ compilation flow:
//
// Source Code (.cpp, .h)
//        ↓
// [Preprocessor] → Macro expansion, #include
//        ↓
// [Compiler] → Syntax check, optimization
//        ↓
// Object Files (.o, .obj)
//        ↓
// [Linker] → Combines objects, resolves symbols
//        ↓
// Executable (.exe, or no extension on Linux)
//
// Characteristics:
// ✓ Maximum performance (runs directly on CPU)
// ✓ Type errors caught at compile time
// ✓ Full control over memory and hardware
// ✗ Platform-specific binaries (need recompile)
// ✗ Longer build times

C#: Compiled to IL, Then JIT

C# Compilation Pipeline 
// C# compilation flow (two-stage):
//
// Source Code (.cs)
//        ↓
// [Roslyn Compiler]
//        ↓
// IL Code (.dll, .exe) ← Intermediate Language (CIL/MSIL)
//        ↓
// [CLR - Common Language Runtime]
//        ↓
// [JIT Compiler] → Compiles to native at runtime
//        ↓
// Native Machine Code (cached)
//
// Characteristics:
// ✓ Type errors caught at compile time
// ✓ Platform independent IL (runs on any .NET runtime)
// ✓ JIT optimizes for specific CPU at runtime
// ✓ Automatic memory management (GC)
// ✗ JIT startup overhead (mitigated by AOT in .NET 8+)

Static vs Dynamic Typing

What is Type Checking?

Type checking is the process of verifying that operations in your code are performed on compatible data types. The question is: when does this checking happen?

Aspect Dynamic Typing (Python) Static Typing (C++/C#)
When types are checked At runtime (when code executes) At compile time (before code runs)
Variable types Can change during execution Fixed at declaration
Type declarations Optional (type hints available) Required (with inference in some cases)
Error discovery When problematic line runs During compilation
IDE support Limited autocomplete Full IntelliSense/autocomplete
Refactoring Risky (errors may hide) Safe (compiler catches issues)
Python - Dynamic Typing 
# Variable type can change
x = 42          # x is int
x = "hello"     # x is now str (no error!)
x = [1, 2, 3]   # x is now list

# Type error discovered at RUNTIME
def add_numbers(a, b):
    return a + b

add_numbers(5, 10)       # Works: 15
add_numbers("5", 10)     # TypeError at runtime!

# Duck typing: "If it walks like a duck..."
def get_length(obj):
    return len(obj)  # Works for any object with __len__

get_length([1,2,3])   # 3 (list)
get_length("hello")   # 5 (string)
get_length({'a':1})   # 1 (dict)
C# - Static Typing 
// Type is fixed at declaration
int x = 42;
// x = "hello";  // Compile ERROR: Cannot convert string to int

// Type inference with var (still statically typed)
var y = 42;      // Compiler infers: int
// y = "hello";  // Compile ERROR: y is still int

// Type errors caught at COMPILE time
int AddNumbers(int a, int b) {
    return a + b;
}

AddNumbers(5, 10);      // Works: 15
// AddNumbers("5", 10);  // Compile ERROR!

// Generics for type-safe polymorphism
int GetLength<T>(ICollection<T> collection) {
    return collection.Count;
}

GetLength(new List<int> {1,2,3});  // 3

Memory Models: Stack vs Heap

Understanding Memory Layout

When your program runs, it uses two main memory regions: the Stack (fast, automatic, limited) and the Heap (slower, manual/GC, unlimited). Where data lives affects performance and lifetime.

Characteristic Stack Heap
Allocation Speed Extremely fast (just move pointer) Slower (find free block, track it)
Deallocation Automatic (function returns) Manual (C++) or GC (C#, Python)
Size Limited (1-8 MB typical) Limited only by system RAM
Lifetime Function scope only Until explicitly freed or GC'd
Thread Safety Thread-local (safe) Shared (needs synchronization)
What lives here Local variables, function params, return addresses Objects, arrays, dynamic data
C++ - Explicit Stack/Heap Control 
// STACK allocation - fast, automatic cleanup
void stackExample() {
    int x = 42;                  // Stack
    double arr[100];             // Stack (fixed size)
    Person person{"Ali", 25};    // Stack
}  // All automatically cleaned up here!

// HEAP allocation - dynamic, manual or smart pointer
void heapExample() {
    // Manual heap (avoid in modern C++)
    int* ptr = new int(42);
    delete ptr;  // Must manually free!

    // Modern C++: Smart pointers (preferred)
    auto smartPtr = std::make_unique<int>(42);
}  // unique_ptr auto-deleted here

// Dynamic array (heap)
std::vector<int> vec;  // Data on heap, vec on stack
vec.push_back(1);      // Heap grows dynamically
C# - Value Types (Stack) vs Reference Types (Heap) 
// VALUE TYPES - live on stack (or inline in objects)
int x = 42;           // Stack
double y = 3.14;      // Stack
bool flag = true;    // Stack
DateTime now = DateTime.Now;  // Stack (struct)

struct Point { int X, Y; }
Point p = new Point();  // Stack!

// REFERENCE TYPES - live on heap
string name = "Ali";  // Heap (reference on stack)
int[] arr = new int[100];  // Heap
Person person = new Person();  // Heap
List<int> list = new();  // Heap

// GC handles heap cleanup automatically
// No delete needed - GC runs when needed

Value Types vs Reference Types

Critical Concept!

This is one of the most important concepts when transitioning from Python. Understanding value vs reference semantics prevents many bugs.

Python - Everything is a Reference 
# In Python, variables are references to objects

# Immutable types (int, str, tuple) - safe
a = 5
b = a      # b references same 5
b = 10     # b now references new object
print(a)   # Still 5 (a unchanged)

# Mutable types (list, dict) - careful!
list1 = [1, 2, 3]
list2 = list1      # Same object!
list2.append(4)
print(list1)       # [1, 2, 3, 4] - BOTH changed!

# To copy:
list3 = list1.copy()        # Shallow copy
list4 = list1[:]            # Shallow copy
import copy
list5 = copy.deepcopy(list1) # Deep copy
C# - Value vs Reference Semantics 
// VALUE TYPES: Copy the value
int a = 5;
int b = a;   // b is a COPY
b = 10;
Console.WriteLine(a);  // 5 (unchanged)

// REFERENCE TYPES: Copy the reference
List<int> list1 = new() {1, 2, 3};
List<int> list2 = list1;  // Same object!
list2.Add(4);
Console.WriteLine(list1.Count); // 4 - BOTH!

// To copy a list:
List<int> list3 = new(list1);  // Copy constructor
List<int> list4 = list1.ToList(); // LINQ copy

// Structs are value types
struct Point { public int X, Y; }
Point p1 = new() { X = 1, Y = 2 };
Point p2 = p1;  // COPY (struct = value type)
p2.X = 100;
Console.WriteLine(p1.X);  // 1 (unchanged)

05Functions & Methods

What is a Function?

A function is a reusable block of code that performs a specific task. Functions help organize code, avoid repetition (DRY - Don't Repeat Yourself), and make programs easier to understand and maintain.

  • Parameters: Input values the function receives
  • Return value: Output the function produces
  • Side effects: Changes the function makes outside itself (e.g., printing, modifying global variables)
Function vs Method

Function: A standalone block of code (e.g., print() in Python).
Method: A function that belongs to a class/object (e.g., list.append()). Methods have access to the object's data via self (Python), this (C++/C#).

Lambda Functions (Anonymous Functions)

What is a Lambda Function?

A lambda function (also called an anonymous function) is a small, unnamed function defined inline. Instead of using def or declaring a named function, you create a function "on the fly" exactly where you need it.

Why use lambdas?

  • Short, one-time-use functions (no need to name them)
  • Passing simple logic to higher-order functions (map, filter, sort)
  • Callbacks and event handlers
  • Cleaner code when the function body is trivial

C++ destructors are deterministic - they run exactly when the object goes out of scope. This pattern (RAII) is fundamental to C++ and ensures resources are always cleaned up. Python's __del__ is not guaranteed to run, and C# uses garbage collection with optional IDisposable.

6.5 Polymorphism (Virtual Methods)

⚠️ Critical Difference: Virtual Methods

In Python, all methods are virtual by default. In C++ and C#, you must mark methods as virtual to enable polymorphism. Forgetting this is a common bug!

Python (automatic) 
# All methods are virtual by default!
def make_speak(animal):
    print(animal.speak())  # Always calls correct version

animals = [Dog("Rex"), Cat("Whiskers")]
for a in animals:
    make_speak(a)  # Polymorphic call
C++ (explicit virtual) 
// Base class MUST have virtual methods
class Shape {
public:
    virtual double area() const = 0;  // Pure virtual
    virtual ~Shape() = default;       // Virtual destructor!
};

void printArea(const Shape& shape) {
    std::cout << shape.area();  // Polymorphic
}

std::vectorShape>> shapes;
shapes.push_back(std::make_unique<Circle>(5));
shapes.push_back(std::make_unique<Rectangle>(3, 4));

for (const auto& s : shapes) {
    printArea(*s);  // Calls correct area()
}
C# (explicit virtual) 
// Must mark methods as virtual
class Shape {
    public virtual double Area() => 0;
}

void PrintArea(Shape shape) {
    Console.WriteLine(shape.Area());
}

List<Shape> shapes = new() {
    new Circle(5),
    new Rectangle(3, 4)
};

foreach (var s in shapes) {
    PrintArea(s);  // Polymorphic
}

💡 Prefer Composition Over Inheritance

The classic OOP advice: "Favor composition over inheritance." Inheritance creates tight coupling; composition is more flexible. Use inheritance for "is-a" relationships, composition for "has-a".

Defines a one-to-many dependency where multiple observers are notified when a subject's state changes. Essential for event-driven systems and UI frameworks.

from abc import ABC, abstractmethod
from typing import List

class Observer(ABC):
    @abstractmethod
    def update(self, message: str): pass

class Subject:
    def __init__(self):
        self._observers: List[Observer] = []
    
    def attach(self, observer: Observer):
        self._observers.append(observer)
    
    def detach(self, observer: Observer):
        self._observers.remove(observer)
    
    def notify(self, message: str):
        for observer in self._observers:
            observer.update(message)

class EmailSubscriber(Observer):
    def __init__(self, email: str):
        self.email = email
    
    def update(self, message: str):
        print(f"Email to {self.email}: {message}")

Encapsulates a request as an object, allowing parameterization, queuing, logging, and undoable operations.

9.1.2 std::unique_ptr (Exclusive Ownership)

💡 Most Common Smart Pointer

unique_ptr should be your default choice for heap allocations. It has zero overhead compared to raw pointers and guarantees automatic cleanup.

unique_ptr Basics 
#include <memory>

// Create with make_unique (preferred, C++14)
auto ptr = std::make_unique<Person>("Ali", 25);

// Or with constructor (C++11)
std::unique_ptr<Person> ptr2(new Person("Sara", 30));

// Access (just like raw pointer)
std::cout << ptr->name;   // "Ali"
std::cout << (*ptr).age;  // 25

// Get raw pointer (non-owning)
Person* raw = ptr.get();

// Check if valid
if (ptr) { /* not null */ }

// Release ownership (returns raw pointer)
Person* released = ptr.release();
// ptr is now nullptr, YOU own released

// Reset (delete and optionally assign new)
ptr.reset();  // Delete and set to nullptr
ptr.reset(new Person("New", 20));  // Delete old, assign new

// auto ptr2 = ptr1;  // ERROR: deleted copy constructor

// ✅ Can move (transfer ownership)
auto ptr2 = std::move(ptr1);
// ptr1 is now nullptr, ptr2 owns the object

// Returning from function (implicit move)
std::unique_ptr<Person> createPerson() {
    return std::make_unique<Person>("New", 0);
}

auto p = createPerson();  // Ownership transferred to p

// Passing to function (transfer ownership)
void takePerson(std::unique_ptr<Person> p) {
    // p is deleted when function exits
}
takePerson(std::move(ptr2));  // Must use move!

// Passing for observation (no ownership transfer)

    std::cout << p.name;
}
observePerson(*ptr);  // Dereference and pass reference

9.1.3 std::shared_ptr (Shared Ownership)

📝 Reference Counting

shared_ptr uses reference counting. Object is deleted when the last shared_ptr goes out of scope. Has slight overhead compared to unique_ptr.

shared_ptr Basics 
#include <memory>

// Create with make_shared (preferred)
auto ptr1 = std::make_shared<Person>("Ali", 25);
std::cout << ptr1.use_count();  // 1

// Copy creates shared ownership
auto ptr2 = ptr1;  // ✅ Can copy!
std::cout << ptr1.use_count();  // 2
std::cout << ptr2.use_count();  // 2

// Both point to same object
ptr1->age = 30;
std::cout << ptr2->age;  // 30

{
    auto ptr3 = ptr1;
    std::cout << ptr1.use_count();  // 3
}  // ptr3 destroyed, count = 2

std::cout << ptr1.use_count();  // 2

// Object deleted when count reaches 0
ptr1.reset();  // count = 1
ptr2.reset();  // count = 0, object deleted!
shared_ptr Use Cases 
// ✅ GOOD: Multiple owners need access
class Node {
public:
    int value;
    std::vectorNode>> children;
    
    void addChild(std::shared_ptr<Node> child) {
        children.push_back(child);
    }
};

// Shared between multiple parents
auto sharedChild = std::make_shared<Node>();
sharedChild->value = 42;

auto parent1 = std::make_shared<Node>();
auto parent2 = std::make_shared<Node>();

parent1->addChild(sharedChild);
parent2->addChild(sharedChild);
// sharedChild.use_count() = 3

// ✅ GOOD: Caching / object pools
std::unordered_mapstring, std::shared_ptr<Texture>> cache;

std::shared_ptr<Texture> getTexture(const std::string& name) {
    auto it = cache.find(name);
    if (it != cache.end()) return it->second;
    
    auto tex = std::make_shared<Texture>(name);
    cache[name] = tex;
    return tex;
}

9.1.4 std::weak_ptr (Non-Owning Observer)

⚠️ Breaking Circular References

weak_ptr observes a shared_ptr without increasing reference count. Essential for preventing memory leaks from circular references.

weak_ptr Basics 
#include <memory>

auto shared = std::make_shared<Person>("Ali", 25);
std::weak_ptr<Person> weak = shared;

std::cout << shared.use_count();  // 1 (weak doesn't count!)

// Cannot access directly - must lock first
if (auto locked = weak.lock()) {
    // locked is a shared_ptr, object exists
    std::cout << locked->name;  // "Ali"
} else {
    // Object was deleted
}

// Check if expired
if (!weak.expired()) {
    // Object still exists
}

// After shared is destroyed
shared.reset();
std::cout << weak.expired();  // true

auto locked = weak.lock();
if (!locked) {
    // Object is gone
}
Solving Circular Reference 
// ❌ BAD: Circular reference = memory leak
class BadNode {
public:
    std::shared_ptr<BadNode> next;
    std::shared_ptr<BadNode> prev;  // Leak!
};

auto a = std::make_shared<BadNode>();
auto b = std::make_shared<BadNode>();
a->next = b;
b->prev = a;  // Circular! Never deleted

// ✅ GOOD: Use weak_ptr for back-references
class GoodNode {
public:
    std::shared_ptr<GoodNode> next;
    std::weak_ptr<GoodNode> prev;  // No ownership
};

auto a = std::make_shared<GoodNode>();
auto b = std::make_shared<GoodNode>();
a->next = b;
b->prev = a;  // OK! a owns b, b observes a

// Access parent
if (auto parent = b->prev.lock()) {
    // Use parent...
}

9.1.6 Rvalue References (T&&) - Move Semantics

Move Semantics 
// Rvalue reference binds to temporaries
int&& rref = 42;        // OK: binds to temporary
int x = 10;
// int&& rref2 = x;     // ERROR: x is lvalue
int&& rref2 = std::move(x);  // OK: move casts to rvalue

// Move constructor - steal resources
class Buffer {
    int* data;
    size_t size;
public:
    // Move constructor
    Buffer(Buffer&& other) noexcept
        : data(other.data), size(other.size) {
        other.data = nullptr;  // Leave source empty
        other.size = 0;
    }
    
    // Move assignment
    Buffer& operator=(Buffer&& other) noexcept {
        if (this != &other) {
            delete[] data;
            data = other.data;
            size = other.size;
            other.data = nullptr;
            other.size = 0;
        }
        return *this;
    }
};

Buffer b1;
Buffer b2 = std::move(b1);  // Move, not copy
Perfect Forwarding 
// Universal reference (T&&) in template
template<typename T>
void wrapper(T&& arg) {
    // Forward preserves value category
    process(std::forward(arg));

wrapper(x);      // T = int&, forwards as lvalue

15Common Gotchas

🔴 Don't Forget the Semicolons!

Every statement in C++ and C# must end with ;

🔴 Declare Types Explicitly

You can't just write x = 5 — you need int x = 5; (or var in C#)

🔴 Array Index Bounds

C++ won't stop you from accessing out-of-bounds memory. C# will throw an exception.

🔴 Braces for Blocks

Use { } for code blocks, not indentation. Indentation is only for readability.

🔴 == vs = in Conditions

if (x = 5) assigns 5 to x in C++! Use if (x == 5) for comparison.

✓ Use Modern Standards

Use C++17/20 and C# 10+ features. They're much more Python-like with auto, var, ranges, and pattern matching.
