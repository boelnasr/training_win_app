01SOLID Principles

Five design principles for writing maintainable, flexible, and understandable object-oriented code.

S
Single Responsibility
A class should have only one reason to change.
O
Open/Closed
Open for extension, closed for modification.
L
Liskov Substitution
Subtypes must be substitutable for their base types.
I
Interface Segregation
Many specific interfaces are better than one general.
D
Dependency Inversion
Depend on abstractions, not concretions.

Single Responsibility Example

❌ Bad: Multiple Responsibilities
class User:
    def save_to_database(self): ...
    def send_email(self): ...
    def generate_report(self): ...
✅ Good: Single Responsibility
class User: ...
class UserRepository: ...
class EmailService: ...
class ReportGenerator: ...

02Clean Code Principles

📛
Meaningful Names
Use intention-revealing names. getUserById() not get()
📏
Small Functions

🚫
DRY - Don't Repeat Yourself

💋
KISS - Keep It Simple

🎯
YAGNI - You Aren't Gonna Need It
Don't add functionality until you actually need it.

03Singleton Pattern

Ensures a class has only one instance and provides a global point of access to it.

🎯 Singleton Structure
Singleton
- instance: Singleton
- __init__()
+ get_instance(): Singleton
Python 
class Singleton:
    _instance = None
    
    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

# Usage
s1 = Singleton()
s2 = Singleton()
print(s1 is s2)  # True - same instance

# Thread-safe with decorator
from functools import wraps
from threading import Lock

def singleton(cls):
    instances = {}
    lock = Lock()
    
    @wraps(cls)
    def get_instance(*args, **kwargs):
        with lock:
            if cls not in instances:
                instances[cls] = cls(*args, **kwargs)
        return instances[cls]
    return get_instance

@singleton
class Database:
    def __init__(self):
        self.connection = "Connected"
⚠️ Use Sparingly

Singletons can make testing difficult and hide dependencies. Consider dependency injection as an alternative.

04Factory Pattern

Creates objects without specifying the exact class to create. Delegates instantiation to subclasses or methods.

Factory Method 
from abc import ABC, abstractmethod

# Product Interface
class Button(ABC):
    @abstractmethod
    def render(self): pass

# Concrete Products
class WindowsButton(Button):
    def render(self):
        return "Windows Button"

class MacButton(Button):
    def render(self):
        return "Mac Button"

# Factory
class ButtonFactory:
    @staticmethod
    def create_button(os_type: str) -> Button:
        factories = {
            "windows": WindowsButton,
            "mac": MacButton
        }
        return factories.get(os_type, WindowsButton)()

# Usage
button = ButtonFactory.create_button("mac")
print(button.render())  # "Mac Button"

05Builder Pattern

Constructs complex objects step by step. Separates construction from representation.

Python 
class Pizza:
    def __init__(self):
        self.size = None
        self.cheese = False
        self.pepperoni = False
        self.mushrooms = False

class PizzaBuilder:
    def __init__(self):
        self._pizza = Pizza()
    
    def set_size(self, size: str):
        self._pizza.size = size
        return self  # Return self for chaining
    
    def add_cheese(self):
        self._pizza.cheese = True
        return self
    
    def add_pepperoni(self):
        self._pizza.pepperoni = True
        return self
    
    def add_mushrooms(self):
        self._pizza.mushrooms = True
        return self
    
    def build(self) -> Pizza:
        return self._pizza

# Fluent interface - readable!
pizza = (PizzaBuilder()
    .set_size("large")
    .add_cheese()
    .add_pepperoni()
    .build())

06Adapter Pattern

Converts one interface to another that clients expect. Acts as a bridge between incompatible interfaces.

Python 
# Existing class with incompatible interface
class OldPaymentSystem:
    def make_payment(self, amount):
        return f"Old system: paid ${amount}"

# New interface we want
class PaymentProcessor(ABC):
    @abstractmethod
    def process(self, amount): pass

# Adapter makes old system work with new interface
class PaymentAdapter(PaymentProcessor):
    def __init__(self, old_system: OldPaymentSystem):
        self._old_system = old_system
    
    def process(self, amount):
        # Translate new method to old method
        return self._old_system.make_payment(amount)

# Client code works with new interface
old_system = OldPaymentSystem()
processor = PaymentAdapter(old_system)
processor.process(100)  # Works!

07Decorator Pattern

Adds new functionality to objects dynamically without altering their structure.

Python 
# Base Component
class Coffee:
    def cost(self) -> float:
        return 2.00
    
    def description(self) -> str:
        return "Coffee"

# Decorator Base
class CoffeeDecorator(Coffee):
    def __init__(self, coffee: Coffee):
        self._coffee = coffee

# Concrete Decorators
class MilkDecorator(CoffeeDecorator):
    def cost(self) -> float:
        return self._coffee.cost() + 0.50
    
    def description(self) -> str:
        return self._coffee.description() + ", Milk"

class SugarDecorator(CoffeeDecorator):
    def cost(self) -> float:
        return self._coffee.cost() + 0.25
    
    def description(self) -> str:
        return self._coffee.description() + ", Sugar"

# Usage - Stack decorators!
coffee = Coffee()
coffee = MilkDecorator(coffee)
coffee = SugarDecorator(coffee)

print(coffee.description())  # "Coffee, Milk, Sugar"
print(coffee.cost())         # 2.75

08Facade Pattern

Provides a simplified interface to a complex subsystem. Hides complexity from the client.

Python 
# Complex subsystem classes
class AudioSystem:
    def on(self): print("Audio on")
    def set_volume(self, level): print(f"Volume: {level}")

class VideoPlayer:
    def on(self): print("Video on")
    def play(self, movie): print(f"Playing: {movie}")

class Lights:
    def dim(self, level): print(f"Lights: {level}%")

# Facade - Simple interface
class HomeTheaterFacade:
    def __init__(self):
        self.audio = AudioSystem()
        self.video = VideoPlayer()
        self.lights = Lights()
    
    def watch_movie(self, movie: str):
        """One simple method does everything!"""
        self.lights.dim(10)
        self.audio.on()
        self.audio.set_volume(50)
        self.video.on()
        self.video.play(movie)

# Client - Super simple!
theater = HomeTheaterFacade()
theater.watch_movie("Inception")

09Observer Pattern

Defines a one-to-many dependency. When one object changes, all dependents are notified.

Python 
from abc import ABC, abstractmethod
from typing import List

# Observer Interface
class Observer(ABC):
    @abstractmethod
    def update(self, message: str): pass

# Subject (Publisher)
class NewsAgency:
    def __init__(self):
        self._observers: List[Observer] = []
    
    def subscribe(self, observer: Observer):
        self._observers.append(observer)
    
    def unsubscribe(self, observer: Observer):
        self._observers.remove(observer)
    
    def notify(self, news: str):
        for observer in self._observers:
            observer.update(news)

# Concrete Observers
class EmailSubscriber(Observer):
    def __init__(self, email: str):
        self.email = email
    
    def update(self, message: str):
        print(f"Email to {self.email}: {message}")

class SMSSubscriber(Observer):
    def __init__(self, phone: str):
        self.phone = phone
    
    def update(self, message: str):
        print(f"SMS to {self.phone}: {message}")

# Usage
agency = NewsAgency()
agency.subscribe(EmailSubscriber("user@example.com"))
agency.subscribe(SMSSubscriber("555-1234"))

agency.notify("Breaking News!")  # Both get notified

10Strategy Pattern

Defines a family of algorithms, encapsulates each one, and makes them interchangeable.

Python 
from abc import ABC, abstractmethod

# Strategy Interface
class PaymentStrategy(ABC):
    @abstractmethod
    def pay(self, amount: float) -> str: pass

# Concrete Strategies
class CreditCardPayment(PaymentStrategy):
    def __init__(self, card_number: str):
        self.card = card_number
    
    def pay(self, amount: float) -> str:
        return f"Paid ${amount} with card {self.card[-4:]}"

class PayPalPayment(PaymentStrategy):
    def __init__(self, email: str):
        self.email = email
    
    def pay(self, amount: float) -> str:
        return f"Paid ${amount} via PayPal ({self.email})"

# Context
class ShoppingCart:
    def __init__(self):
        self._strategy: PaymentStrategy = None
    
    def set_payment_strategy(self, strategy: PaymentStrategy):
        self._strategy = strategy
    
    def checkout(self, amount: float):
        return self._strategy.pay(amount)

# Usage - Switch strategies at runtime
cart = ShoppingCart()

cart.set_payment_strategy(CreditCardPayment("1234-5678-9012-3456"))
print(cart.checkout(100))  # Paid $100 with card 3456

cart.set_payment_strategy(PayPalPayment("user@email.com"))
print(cart.checkout(50))   # Paid $50 via PayPal

11Command Pattern

Encapsulates a request as an object. Enables undo/redo, queuing, and logging of operations.

Python 
from abc import ABC, abstractmethod

# Command Interface
class Command(ABC):
    @abstractmethod
    def execute(self): pass
    
    @abstractmethod
    def undo(self): pass

# Receiver
class TextEditor:
    def __init__(self):
        self.text = ""
    
    def write(self, text: str):
        self.text += text
    
    def delete(self, count: int):
        self.text = self.text[:-count]

# Concrete Commands
class WriteCommand(Command):
    def __init__(self, editor: TextEditor, text: str):
        self.editor = editor
        self.text = text
    
    def execute(self):
        self.editor.write(self.text)
    
    def undo(self):
        self.editor.delete(len(self.text))

# Invoker with history
class CommandHistory:
    def __init__(self):
        self._history = []
    
    def execute(self, command: Command):
        command.execute()
        self._history.append(command)
    
    def undo(self):
        if self._history:
            command = self._history.pop()
            command.undo()

# Usage
editor = TextEditor()
history = CommandHistory()

history.execute(WriteCommand(editor, "Hello "))
history.execute(WriteCommand(editor, "World"))
print(editor.text)  # "Hello World"

history.undo()
print(editor.text)  # "Hello "

12MVC / MVVM Patterns

🏛️
MVC
Model - View - Controller
Separates data (Model), UI (View), and logic (Controller).
Use for: Web apps, traditional GUIs
🔗
MVVM
Model - View - ViewModel
ViewModel exposes data & commands for data binding.
Use for: WPF, modern JS frameworks
📊
MVP
Model - View - Presenter
Presenter handles all logic, View is passive.
Use for: Android, testable UIs

13Dependency Injection

Dependencies are injected rather than created inside the class. Enables loose coupling and testing.

❌ Tightly Coupled
class OrderService:
    def __init__(self):
        # Creates its own dependency!
        self.db = MySQLDatabase()
        self.email = SMTPEmailer()
✅ Dependency Injection
class OrderService:
    def __init__(self, db: Database, 
                 email: Emailer):
        # Dependencies injected!
        self.db = db
        self.email = email
Dependency Injection Container 
# Simple DI Container
class Container:
    def __init__(self):
        self._services = {}
    
    def register(self, interface, implementation):
        self._services[interface] = implementation
    
    def resolve(self, interface):
        return self._services[interface]()

# Usage
container = Container()
container.register(Database, MySQLDatabase)
container.register(Emailer, SMTPEmailer)

# Resolve dependencies
db = container.resolve(Database)
email = container.resolve(Emailer)
service = OrderService(db, email)

14Repository Pattern

Abstracts data access logic. Mediates between the domain and data mapping layers.

Python 
from abc import ABC, abstractmethod
from typing import List, Optional

# Entity
class User:
    def __init__(self, id: int, name: str, email: str):
        self.id = id
        self.name = name
        self.email = email

# Repository Interface
class UserRepository(ABC):
    @abstractmethod
    def get_by_id(self, id: int) -> Optional[User]: pass
    
    @abstractmethod
    def get_all(self) -> List[User]: pass
    
    @abstractmethod
    def save(self, user: User): pass
    
    @abstractmethod
    def delete(self, id: int): pass

# Concrete Implementation
class SQLUserRepository(UserRepository):
    def __init__(self, connection):
        self.conn = connection
    
    def get_by_id(self, id: int) -> Optional[User]:
        # SQL query here
        pass
    
    def get_all(self) -> List[User]:
        # SQL query here
        pass
    
    def save(self, user: User):
        # SQL INSERT/UPDATE
        pass
    
    def delete(self, id: int):
        # SQL DELETE
        pass

# Service uses abstraction
class UserService:
    def __init__(self, repo: UserRepository):
        self.repo = repo  # Depends on interface!
    
    def get_user(self, id: int) -> User:
        return self.repo.get_by_id(id)
💡 Benefits of Repository Pattern
  • Decouples business logic from data access
  • Easy to swap databases (SQL → MongoDB)
  • Simplifies unit testing with mock repositories
  • Centralizes data access logic

15Pattern Selection

ScenarioPatternWhy
Runtime compositionFactory / DISwap implementations without rewiring
Cross-cutting behaviorDecoratorStack behaviors like logging or caching
Complex constructionBuilderReadable, testable creation logic
Event-driven flowsObserverLoose coupling between producers/consumers
⚠️ Avoid Pattern Overuse

Patterns are tools, not requirements. Prefer simpler code until complexity justifies a pattern.

16Testing & Review

✅ Review Checklist
  • Is the pattern solving a real pain point?
  • Are dependencies injected for testability?
  • Is the abstraction stable under change?
  • Does the pattern hide too much complexity?

17Maintenance

🔧 Long-Term Care

Refactor when patterns become excessive, document the intent, and keep constructors small by pushing complex setup into factories.
